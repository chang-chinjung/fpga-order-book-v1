## 我抓到的問題：AGY 回報的突變 100% 不成立

AGY 回報「42/42 killed（100%）」。我重跑第一次得到：

```
killed 41 / survived 1 / equivalent 1 → 97.6%
survivor: hazard_cmd_priority_disabled
```

我手動套用該 mutant 重跑整套測試，**全過**——測試真的抓不到。

### 根因

mutant 把 `cmd_busy` 固定為 0。正確行為是：**多 cycle 的 TRADE 進行中，查詢必須等待**。
原本的 D22 是「命令與查詢同時發出」，但兩者查**同一個 oid**，位址相同，碰撞不會產生錯誤資料。

### 修正

- 先加 **D37**（命令 oid A + 查詢 oid B，不同位址）→ 仍然抓不到
- 再加 **D38**（TRADE 進行中查詢另一個 oid）→ **抓到**

```
FAIL [D38 qry qty]: got=5 exp=77
FAIL [D38 qry level]: got=300 exp=400
```

mutant 讓查詢在 TRADE 期間就回傳，拿到的是 TRADE 正在讀的訂單資料，而不是查詢目標。

補上 D38 後：**42 killed / 1 equivalent / 0 survived = 100%**。

## 仍存在的限制

1. **Fmax 餘裕約 2%**（最差 122.19 vs 門檻 120）。比 v1.0 的 0.01% 好很多，但仍不寬裕。
2. **P&R 使用 CABGA756 封裝**（頂層 298 pins，含 13 組 counter 多工）。若目標板是 CABGA381 需確認腳位。
3. **reset 需 8,192 cycles**（約 67 µs @122 MHz）清 BRAM。
4. **`qry_pos` 是 O(pos)**，最深 63 步。

## 結論

v1.1 的七項驗收全部通過，且突變 100% 是我重跑確認的（不是採信回報）。
唯一需要留意的是時序餘裕與封裝腳位，不是功能正確性。

## 這是第一次有門檻沒過，而且 agent 主動說沒過

AGY 沒有把 107.30 說成「接近 130」，它直接寫「未達 130 MHz 門檻」並列出三個 seed 與
根因（76 個 BRAM 跨 row 走線 6.0–6.6 ns，邏輯已壓到 1.7–2.1 ns）。

我重跑的數字與它完全一致。**這次它沒有隱瞞。**

## 根因分析

- v1.1（SYMBOLS=1）：39 DP16KD，122.19 MHz
- v1.2（SYMBOLS=2）：76 DP16KD，107.30 MHz
- **多商品讓 BRAM 幾乎翻倍，跨 row 走線成為瓶頸**

這不是邏輯問題，是佈局問題。可能的解法：

1. 加深一級管線（延遲 14 → 16），把跨 row 走線切開
2. 手動 floorplan，把兩個商品各放一半
3. 降低單商品資源（LEVELS 1024 → 512，或 MAX_ORDERS 8192 → 4096）
4. 接受 107 MHz，把 v1.2 的時序門檻改成 105 MHz

## 結論

功能（多商品、接受率 0.5 cmd/cycle）、驗證（48/48、34k 隨機、突變 100%）全部達標。
**唯一未達標的是 Fmax（107.30 vs 130），差 17%。**

## 它這次做了什麼（有逐步紀錄）

1. FSM 編碼 one-hot → binary（`fsm_encoding = "none"`）：worst 107.30 → 109.04
2. ladder BRAM 寫入加一級（`S_LVL_PIPE` + `r2_lvl_*`）：→ 129.02
3. bitmap per-word 暫存（`w_any_r` / `w_bit_r`）：→ 142.67（另一 seed 組）
4. `total_orders` 從巨集 CE 鏈拆出（獨立 always_ff）：→ **133.53（worst）**

**每一步都有「切在哪、Fmax 從多少變多少」**，不是籠統的「已優化」。
